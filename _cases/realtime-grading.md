## 문제

원어민 강사가 채점해 결과까지 평균 3.5일이 걸렸다. 학생은 제출 직후 결과를 봐야 해서 무거운 모델은 쓸 수 없었다. LLM 프로토타입은 금방 만들었지만, 초기 운영에서 아래 문제가 나왔다.

| 증상 | 원인 | 영향 |
|---|---|---|
| 다시 채점하면 점수가 달라진다. | 같은 입력에도 LLM이 다른 결과를 낼 수 있다. | 채점 결과를 신뢰하기 어렵다. |
| 정해진 형식과 다른 출력이 나온다. | 출력 형식을 강제하지 않았다. | 파싱에 실패하면 결과를 돌려줄 수 없다. |
| 응답이 끝나지 않는다. | 글자 수만 채우려고 무의미한 문자를 반복한 답안이 제출 필터를 통과했다. | 응답이 끝나지 않아 결과를 돌려줄 수 없다. |

## 판단

**LLM이 판단할 범위를 줄이고, 채점 항목 단위로 나눠 동시에 채점했다.**

| 대안 | 장점 | 고르지 않은 이유 |
|---|---|---|
| 한 프롬프트로 rubric 전체 채점 | 한 번만 호출하면 된다. | 출력이 길어 느리고, 여러 기준의 판단이 섞인다. |
| 채점 항목 순차 호출 | 항목별 판단 범위를 좁힐 수 있다. | 항목 수에 따라 처리 시간이 늘어난다. |
| 큰 reasoning 모델 유지 | 비교한 모델 중 품질이 가장 좋았다. | 실시간 응답에 필요한 시간 한도를 넘었다. |
| 비동기 채점 후 알림 | 응답 시간의 제약을 줄일 수 있다. | 제출 직후 피드백을 줄 수 없다. |

- **LLM 판단 범위를 줄였다.** 코드나 NLP 모델로 계산할 수 있는 기준은 코드로 옮겼다. 남은 기준은 rubric과 예시를 구체화했다.
- **breakpoint는 평가 데이터셋으로 정했다.** 모델과 reasoning 단계 조합을 비교하고, 콘텐츠팀이 결과를 확인했다. 품질 기준을 지키는 조합 중 가장 빠른 것을 골랐다.

{% include diagrams/realtime-grading-breakpoint.html %}

- **Structured Output은 처음에 쓰지 않았다.** 적용하면 응답이 느려지고 채점 품질도 떨어졌다. 대신 프롬프트 I/O 계약에 정의한 키와 타입을 코드로 검증했다.
- **스키마를 고친 뒤 도입했다.** 모델을 바꾸고, 필드 순서를 바꾸고, 중첩을 줄였다. 그러자 품질 저하가 줄었다.

## 구현

{% include diagrams/realtime-grading.html %}

- **예외 입력에 맞춰 전처리를 고쳤다.** 제출 필터를 통과한 답안 중 어떤 입력이 LLM 오류를 일으키는지 분석하고, AI 서버의 전처리 로직을 개선했다.
- **초기 운영의 예외 입력 오류가 줄었다.** 항목별 재시도와 출력 스키마 검증을 도입하고, OpenAI 모델 버전을 업데이트한 뒤 오류가 감소했다.
- **검증에 실패한 항목만 다시 호출했다.** 한 항목의 실패로 제출물 전체의 채점이 실패하는 일을 줄이기 위해서다.
- **Speaking에서는 채점 단계를 맡았다.** 다른 담당자가 처리한 STT·Vision 인식 결과를 받아 채점했다.
- **성능을 확인하며 적용 범위를 넓혔다.** 과제마다 rubric과 답안 분포가 달라 일부 과제부터 적용했다.

출력 형식을 검증하고 재시도하는 것은 채점 결과를 반환하기 위한 처리다. 반환한 결과가 rubric에 맞는지는 별도로 검증해야 했다. [사례 2]({{ '/portfolio/quality-loop/' | absolute_url }})에서는 개발과 운영의 오채점을 발견하고 개선한 과정을 다룬다.
