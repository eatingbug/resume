## 문제

원어민 강사가 채점해 결과까지 평균 3.5일이 걸렸다. 학생은 제출 직후 결과를 봐야 해서 무거운 모델은 쓸 수 없었다. LLM 프로토타입은 금방 만들었지만, 초기 운영에서 아래 문제가 나왔다.

| 증상 | 원인 | 영향 |
|---|---|---|
| 재채점 시 점수 변동 | LLM 출력의 비결정성 | 채점 신뢰 저하 |
| 출력 형식 깨짐 | 출력 형식 강제 없음 | 파싱 실패 → 결과 미반환 |
| 응답이 끝나지 않음 | 글자 수 채우기용 무의미 문자 반복 답안이 제출 필터를 간신히 통과 | 응답 미종료 → 결과 미반환 |

## 판단

**LLM이 판단할 범위를 줄이고, 채점 항목 단위로 나눠 동시에 채점했다.**

| 대안 | 장점 | 고르지 않은 이유 |
|---|---|---|
| 한 프롬프트로 rubric 전체 채점 | 호출 한 번 | 출력이 길어 느림, 기준 간 판단 혼재 |
| 채점 항목 순차 호출 | 항목별 판단 범위가 좁음 | 항목 수만큼 시간 증가 |
| 큰 reasoning 모델 유지 | 품질 최고 | 실시간 한도 초과 |
| 비동기 채점 후 알림 | 시간 제약 없음 | 실시간 피드백 포기 |

- **LLM 판단 범위를 줄였다.** 코드나 NLP 모델로 계산할 수 있는 기준은 코드로 옮겼다. 남은 기준은 rubric과 예시를 구체화했다.
- **breakpoint는 평가 데이터셋으로 정했다.** 모델과 reasoning 단계 조합을 비교하고, 콘텐츠팀이 결과를 확인했다. 품질 기준을 지키는 조합 중 가장 빠른 것을 골랐다.

{% include diagrams/realtime-grading-breakpoint.html %}

- **Structured Output은 처음에 쓰지 않았다.** 적용하면 응답이 느려지고 채점 품질도 떨어졌다. 대신 프롬프트 I/O 계약에 정의한 키와 타입을 코드로 검증했다.
- **스키마를 고친 뒤 도입했다.** 모델을 바꾸고, 필드 순서를 바꾸고, 중첩을 줄였다. 그러자 품질 저하가 줄었다.

## 구현

{% include diagrams/realtime-grading.html %}

- **텍스트 전처리:** 필터를 간신히 통과한 입력의 LLM 오류 원인 분석 → AI 서버 전처리 로직 지속 개선
- **예외 입력 오류 감소:** 초기 운영의 주요 문제. 항목 단위 재시도, 출력 스키마 검증, OpenAI 모델 버전 업데이트 이후 감소
- **항목 단위 재시도:** 출력 검증 실패 시 그 채점 항목만 재호출 → 제출물 전체 실패 방지
- **Speaking 범위:** STT·Vision 인식 결과를 받는 채점 단계까지 담당
- **단계적 확대:** 일부 과제부터 적용 → 성능 확인 후 확대 (과제마다 rubric·답안 분포가 다름)
