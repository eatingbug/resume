## 문제

LLM 채점은 같은 답안에도 다른 결과를 낼 수 있다. 콘텐츠팀은 AI 결과와 학생 문의를 엑셀로 하나씩 검수했다. 오류가 쌓여도 judge 기준이나 Ground Truth로 돌아가지 않았다.

| 상황 | 영향 |
|---|---|
| 개발 초기에 운영 데이터 없음 | 평가 데이터셋을 만들 데이터가 없음 (콜드 스타트) |
| 엑셀 수작업 검수 | 오류 유형이 기록으로 남지 않음 |
| 전수 judge 불가 | 운영 trace 월 약 7만~15만 건, judge 비용 부담 |

## 판단

**운영 트래픽 일부만 judge로 검증하고, 그 결과 일부를 AI팀이 매일 확인했다.**

| 대안 | 장점 | 고르지 않은 이유 |
|---|---|---|
| 엑셀 수작업 검수 유지 | 추가 도구 없음 | 오류 유형이 기록으로 남지 않음 |
| 운영 전수 judge | 누락 없음 | judge 비용 |
| 사람 전수 검수 | 판단 신뢰도 높음 | 로그가 많아 전부 볼 수 없음 |

- **평가 데이터셋은 외부 데이터로 시작했다.** 개발 초기에는 운영 데이터가 없어 다른 팀의 데이터를 썼다. 지금은 운영 데이터로 Langfuse에 쌓는다.
- **Ground Truth는 혼자 정하지 않았다.** 콘텐츠팀, 프롬프트 엔지니어와 협의해 정했다. 점수는 콘텐츠팀 여럿이 같은 답안을 채점하고, 차이를 조정해 확정했다.
- **지표는 글쓰기 채점 연구에서 골랐다.** 연구 자료와 여러 사례에서 쓰는 지표를 찾아봤다. 그중 QWK가 우리 채점에 맞았다.
- **표본은 10%로 정했다.** judge 비용과 전체 trace 규모를 보고 판단했고, 이후 통계로 확인했다. 과제 유형별 평균 월 400~900건이면 오류율 추정 오차는 약 ±3~5%p(95% 신뢰)다.
- **가장 어려운 것은 수용 기준이었다.** 어느 성능까지 받아들일지, 잘못 채점된 경우를 어떻게 관리할지를 정해야 했다.

## 구현

{% include diagrams/quality-loop.html %}

- **검수 전환:** 엑셀 수작업 검수 → Langfuse Annotation 제안·도입
- **재검수 대상:** judge 결과 일부(AI팀, 오류인지 애매하면 콘텐츠팀에 문의), 학생 문의 중 문제 있는 채점(콘텐츠팀)
- **모니터링·개선:** 대시보드, 임계값 알림(Slack·Email). 오채점률이 임계치를 넘고 같은 오류가 반복되면 프롬프트 개선
- **비용 최적화:** 기준 버전 대비 벤치마크로 기능별 경량 모델 교체, reasoning 단계 조정

## 결과

| 지표 | 값 | 측정 기준 |
|---|---|---|
| 자동 검증 규모 | 월 2만~5만 건 | 운영 trace 10% 표본의 채점 항목 단위 judge 건수 |
| 비용 | 94% 절감 | 모델을 교체한 기능의 단가 차이. 전체 비용 기준 아님 |
| 검수 프로세스 | 엑셀 → Langfuse Annotation | 사내 성능검수 위원회의 메인 자료로 활용 |

| 품질 지표 (값 비공개) | 정의 | 판정 · 기준선 |
|---|---|---|
| QWK·AAR·MAE (개발) | AI 점수와 Ground Truth 비교. QWK: 우연 일치 보정 일치도, AAR: ±1점 이내 비율, MAE: 평균 점수 차이 | 콘텐츠팀 합의 점수. 전문가끼리 일치도·기준 버전과 비교 |
| 오채점률 (운영) | judge가 오채점으로 판정한 채점 항목 비율 | LLM-as-a-judge. 팀이 정한 임계치와 비교 |
| judge-사람 일치율 (운영) | 사람이 judge 판정에 동의한 비율 | AI팀 재검수, 애매한 사례는 콘텐츠팀 |

## 한계와 다음 단계

- **수용 기준은 고정할 수 없다.** 객관적인 기준이 없어 팀과 계속 협의한다.
- **judge도 틀린다.** judge 자체의 오류와 놓친 오채점은 Human Annotation으로만 일부 잡는다.
- **적은 과제 유형은 표본이 부족하다.** 과제 유형별 트래픽이 고르지 않다. 다음 단계는 층화 표본 추출이다.
