## 문제

LLM 채점은 출력이 비결정적이라, 몇 건을 눈으로 확인해서는 전체 품질을 말할 수 없다. 그런데 운영과 개발 모두 눈으로 보는 것 말고는 방법이 없었다.

| 단계 | 이전 방식 | 영향 |
|---|---|---|
| 운영 | 성능 모니터링 없음. Langfuse Trace를 하나씩 열어 확인 | 운영 채점이 잘 되고 있는지 판단할 수 없음 |
| 운영 | 학생 문의가 오면 콘텐츠팀이 학생 ID와 토픽을 전달하고, AI팀이 Trace를 직접 조회해 확인 | 제기된 건만 사후에 확인. 확인 결과와 오류 유형이 쌓이지 않음 |
| 개발 | 프롬프트 버전을 바꾸면 엑셀로 콘텐츠팀 검수. 사람이 한 건씩 확인해 검수 건수를 늘리기 어려움 | 검수한 케이스 외의 다른 케이스에서 잘 동작하는지 알 수 없음 |
| 개발 | 정량 지표 없음 | 버전 사이의 성능을 숫자로 비교할 수 없음 |

## 판단

**정답이 있는 개발 단계는 Ground Truth와 비교하고, 정답이 없는 운영 단계는 표본을 judge로 판정한 뒤 사람이 judge를 검수했다.**

| 대안 | 장점 | 고르지 않은 이유 |
|---|---|---|
| 엑셀 검수 유지 (개발) | 추가 도구 없음 | 사람이 한 건씩 확인해야 해서 평가 데이터셋을 크게 늘리기 어려움. 검수한 케이스 외의 다른 케이스에서 잘 동작하는지 알 수 없음 |
| 운영 데이터에도 Ground Truth 부여 | 개발과 같은 지표 사용 | 월 약 7만~15만 건에 사람이 점수를 매길 수 없음 |
| 운영 전수 judge | 누락 없음 | judge 비용 |
| judge만 쓰고 사람 재검수 생략 | 비용 최소 | judge의 오판을 알 수 없음 |

개발 단계

- **평가 데이터셋은 외부 데이터로 시작했다.** 개발 초기에는 운영 데이터가 없어 다른 팀의 데이터를 썼다(콜드 스타트). 지금은 운영 데이터로 Langfuse에 쌓는다.
- **Ground Truth는 콘텐츠팀에 맡겼다.** 콘텐츠팀 여럿이 같은 답안을 채점하고, 차이를 조정해 확정했다.
- **지표는 글쓰기 채점 연구에서 골랐다.** 연구 자료와 여러 사례에서 쓰는 지표를 찾아봤다. 그중 QWK가 우리 채점에 맞았다.
- **콘텐츠팀 검수를 엑셀에서 Langfuse Annotation으로 옮겼다.** 콘텐츠팀이 결과 전체를 보되 Ground Truth와 어긋난 건을 중심으로 훑고, 오채점과 오류 유형을 Langfuse에 남긴다. Ground Truth가 틀렸으면 고친다.

운영 단계

- **표본은 10%로 정했다.** judge 비용과 전체 trace 규모를 보고 판단했고, 이후 통계로 확인했다. 과제 유형별 평균 월 400~900건이면 오류율 추정 오차는 약 ±3~5%p(95% 신뢰)다.
- **judge 결과는 사람이 다시 검수했다.** AI팀이 judge가 오채점으로 판정한 건을 위주로 매일 일부를 확인한다. 사람이 정상으로 보면 judge 오판으로 기록하고, 오판이 자주 나오면 judge 기준을 고친다. 오류인지 애매한 사례는 콘텐츠팀에 넘긴다.
- **학생 문의는 콘텐츠팀이 Langfuse에서 직접 Annotation한다.** AI팀이 Trace를 대신 찾아 주던 방식을 바꿨다. Annotation 매뉴얼을 쓰고, 오류 유형을 콘텐츠팀과 협의해 정했다.

공통

- **가장 어려운 것은 수용 기준이었다.** 어느 성능까지 받아들일지, 잘못 채점된 경우를 어떻게 관리할지를 정해야 했다.

## 구현

{% include diagrams/quality-loop.html %}

- **오류 유형 공유:** 개발의 벤치마크 Annotation, 운영의 judge 재검수, 학생 문의 Annotation이 같은 오류 유형 분류를 쓴다
- **되먹임:** 오류 유형 → judge 기준 수정, Ground Truth 수정, 오채점 사례를 평가 데이터셋에 추가
- **모니터링·개선:** 대시보드, 임계값 알림(Slack·Email). 오채점률이 임계치를 넘고 같은 오류가 반복되면 프롬프트 개선
- **비용 최적화:** 기준 버전 대비 벤치마크로 기능별 경량 모델 교체, reasoning 단계 조정

운영에서 발견한 오채점은 평가 데이터셋과 판정 기준을 고치는 근거가 됐다. 프롬프트를 수정한 뒤에는 변경 전후를 비교하고 운영에 반영할 절차가 필요했다. [사례 3]({{ '/portfolio/prompt-cicd-gate/' | absolute_url }})에서는 이 평가 수단을 변경 검증과 배포에 연결한 과정을 다룬다.

|---|---|---|

| 개발 검증 범위 | 과제 유형 × 채점 항목당 20~30건. 바꿀 때마다 콘텐츠팀이 엑셀로 다시 검수 | 과제 유형 × 채점 항목당 최소 50~100건. Ground Truth와 자동으로 비교 |
| 품질 판단 방법 | 사람이 눈으로 확인 | 개발: QWK·AAR·MAE. 운영: 오채점률, judge-사람 일치율 |
| 오채점을 아는 시점 | 학생 문의가 들어온 뒤 | 오채점률이 임계치를 넘으면 알림 |
| 검수 기록 | 남지 않음 | 오류 유형별로 Langfuse에 쌓임. 사내 성능검수 위원회의 메인 자료로 활용 |
| 비용 | 기능별 품질 차이를 비교할 근거 없음 | 모델을 교체한 기능의 단가 94% 절감. 전체 비용 기준 아님 |

| 품질 지표 (값 비공개) | 정의 | 판정 · 기준선 |
|---|---|---|
| QWK·AAR·MAE (개발) | AI 점수와 Ground Truth 비교. QWK: 우연 일치 보정 일치도, AAR: ±1점 이내 비율, MAE: 평균 점수 차이 | 콘텐츠팀 합의 점수. 전문가끼리 일치도·기준 버전과 비교 |
| 오채점률 (운영) | judge가 오채점으로 판정한 채점 항목 비율 | LLM-as-a-judge. 팀이 정한 임계치와 비교 |
| judge-사람 일치율 (운영) | judge가 오채점으로 판정한 건 중 사람이 동의한 비율 | AI팀 재검수, 애매한 사례는 콘텐츠팀 |

## 한계와 다음 단계

- **수용 기준은 아직 숫자로 확정하지 못했다.** 객관적인 기준이 없어, 팀 논의를 거듭하며 알림과 평가 게이트의 임계치를 조정하고 있다.
- **평가 데이터셋은 아직 작다.** 드문 오류 유형은 평가 데이터셋에 없을 수 있다. 테스트 비용 때문에 케이스를 크게 늘리지 않고, 운영에서 확인한 오채점 사례를 골라 추가한다.
- **judge가 놓친 오채점은 잘 보이지 않는다.** 사람은 judge가 오채점으로 판정한 건을 위주로 보므로, judge가 정상으로 넘긴 오채점은 학생 문의로만 일부 잡힌다.
- **적은 과제 유형은 표본이 부족하다.** 과제 유형별 트래픽이 고르지 않다. 다음 단계는 층화 표본 추출이다.
