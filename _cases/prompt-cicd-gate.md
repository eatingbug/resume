## 문제

팀에 합류했을 때 프롬프트는 Python 코드 안의 문자열이었다. 프롬프트 엔지니어가 채점 기준에 맞게 프롬프트를 고쳐도, AI 엔지니어가 서버를 다시 배포해야 학생에게 반영됐다. 프롬프트 개선이 서버 배포에 묶여 있었다.

그렇다고 프롬프트만 바로 교체할 수도 없었다. LLM 출력은 비결정적이라 작은 수정으로도 채점 품질이 달라질 수 있었다. [사례 2]({{ '/portfolio/quality-loop/' | absolute_url }})에서 만든 품질 측정 수단을, 변경을 채택하고 운영에 반영하는 절차에 연결해야 했다.

| 상황 | 영향 |
|---|---|
| 프롬프트가 Python 코드 안의 문자열 | 읽고 고치기 어렵고, 프롬프트만 바꿔도 서버 재배포 필요 |
| 병합 전 자동 평가 없음 | 변경 전후의 품질을 사람이 확인해야 함 |
| 품질 외에도 지연시간·비용에 차이 발생 | 지표 하나만으로 새 버전의 채택 여부를 정하기 어려움 |

## 판단

**프롬프트 교체는 서버 배포에서 분리하되, 변경의 채택은 자동 평가와 사람 검토를 거치게 했다.**

| 선택지 | 해결하는 문제 | 남은 문제·판단 |
|---|---|---|
| YAML 파일로 분리 | 코드 가독성·유지보수 | 여전히 서버와 함께 배포 |
| 프롬프트 저장소·Langfuse로 분리 | 프롬프트 버전 관리, 재배포 없는 교체 | 변경의 품질을 확인할 절차도 필요 |
| PR 평가 게이트와 staging 테스트 연결 | 병합 전 비교 평가, 운영 반영 전 전체 흐름 확인 | 최종 채택에는 사람 판단 필요 |
| 운영 A/B 테스트 | 실제 트래픽으로 비교 | 성능이 떨어질 수 있는 버전을 학생에게 노출하므로 선택하지 않음 |

- **분리와 검증을 순서대로 붙였다.** 코드 안 문자열을 YAML 파일로 옮기고, 프롬프트 저장소·Langfuse로 분리한 뒤 평가 게이트를 붙였다.
- **자동 검사가 명백한 문제를 막고, 사람은 장단점을 판단한다.** 기준 미달이면 CI가 실패해 병합을 막는다. 품질·지연시간·비용 사이에 장단점이 있으면 평가 리포트와 변경 목적을 보고 최종 채택한다.
- **미세한 차이만으로 변경을 막지는 않았다.** 기준 버전과 큰 차이가 없으면 왜 프롬프트를 바꿨는지 확인하고 대체로 병합한다. 지표별 임계치는 현재 조정 중이다.
- **운영 반영 전에는 학생에게 결과를 보여 주지 않고 확인한다.** staging 환경에서 변경된 프롬프트와 workflow를 실제 운영 데이터로 테스트한다.

## 구현

{% include diagrams/prompt-cicd-gate.html %}

- **PR 단계:** 평가 데이터셋으로 기준 버전과 비교한다. 실패하면 PR 코멘트에 실패 원인·문제 샘플·개선 제안을 남겨 수정한다. 자동 평가 통과 후 사람 리뷰를 거친다.
- **staging 단계:** staging 브랜치에 병합한 뒤, 해당 환경에서 실제 운영 데이터를 사용해 E2E 테스트를 진행한다. 결과는 학생에게 노출하지 않는다.
- **운영 반영:** 개발자가 최종 채택해 운영 브랜치에 병합한다. 프롬프트는 Langfuse에 버전으로 등록하고 production label을 변경해 AI 서버에 반영한다. Langfuse가 제공하는 프롬프트 변경 webhook을 활용했다.
- **교체 범위:** 프롬프트 변경은 서버 재배포 없이 반영한다. workflow 코드가 바뀌면 서버 배포가 필요하다. AI 서버는 이전·새 프롬프트 I/O 계약을 함께 지원해, 호환 범위 안에서는 계약이 다른 버전 사이에서도 교체·롤백할 수 있다.
- **운영 확인:** 반영 후 품질은 사례 2의 운영 표본 평가·대시보드·임계값 알림으로 확인한다.

| 상황 | 대응 경로 |
|---|---|
| 일반 변경, 치명적이지 않은 문제 | 평가 게이트와 검토를 거쳐 새 버전으로 개선 |
| 치명적 문제 | Langfuse production label을 직전 버전으로 롤백하고 webhook으로 반영 |
| 롤백으로 해결할 수 없는 핫픽스 | Langfuse 수동 등록. 평가 게이트를 우회하는 예외 경로 |

**확장: 개선 작업을 연결한 AI Agent 파일럿**

평가 게이트가 없던 초기에는 비개발자가 Langfuse Playground·Experiments에서 결과를 눈으로 확인한 뒤 프롬프트 엔지니어나 개발자에게 전달했다. 실제 수정은 주로 프롬프트 엔지니어와 개발자가 맡아, 비개발자의 작업 절차를 개선하는 것만으로 얻는 효과는 작았다.

이후 콘텐츠팀의 실제 AI 결과 확인 작업이 늘면서, 채점 기준과 Langfuse Trace, 프롬프트 수정, 평가 게이트를 연결한 사내 Agent 서비스를 개발했다. 실제 채점 로그 조회, 오채점 패턴에 따른 프롬프트 수정, 평가 게이트 실행을 각각 Skill로 구성했다.

현재는 사람이 작업을 판단하고 Agent가 해당 단계를 실행한다. 프롬프트 엔지니어와 개발자가 사용하는 파일럿이며, 최종 변경 채택과 운영 반영은 개발자가 맡는다. 모델이 각 Skill을 연결해 개선 워크플로우를 자동으로 수행하도록 개선 중이다.

| 프롬프트 롤백 | 서버 배포에 묶임 | 서버가 지원하는 I/O 계약 범위에서 label 변경·webhook으로 반영 |
| 개선 작업 연결 | 결과를 확인한 뒤 프롬프트 엔지니어나 개발자에게 전달했다. | 조회·수정·평가를 Skill로 구성했다. 사람이 작업을 판단하고 Agent가 실행한다. |

## 한계와 다음 단계

- **병합 임계치는 아직 조정 중이다.** 품질·지연시간·비용과 변경 목적을 함께 고려해야 하며, 수용 기준은 팀 논의로 조정하고 있다.
- **staging에서 확인한 데이터가 운영 전체를 대표하지는 않는다.** 운영 반영 뒤에는 전체에 한 번에 적용된다. 놓친 문제는 운영 표본 평가가 잡을 때까지 학생에게 영향을 줄 수 있다. 다음 단계는 카나리 배포 등 적용 범위를 나누는 것이다.
- **재배포 없는 교체에는 호환 범위가 있다.** 서버가 지원하지 않는 I/O 계약이나 workflow 코드 변경에는 서버 수정·배포가 필요하다.
- **Agent 서비스는 파일럿이다.** 현재 작업 판단은 사람이 맡는다. 모델이 Skill을 연결해 워크플로우를 자동으로 수행하도록 개선 중이다. 콘텐츠팀으로의 사용 확대와 개선 시간 단축 효과는 추가 확인이 필요하다.
