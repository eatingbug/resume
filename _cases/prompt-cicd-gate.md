## 문제

팀에 합류했을 때 프롬프트는 Python 코드 안의 문자열이었다. 읽고 고치기도 어려웠지만, 더 큰 문제는 반영 속도였다. 프롬프트 엔지니어가 채점 기준에 맞게 프롬프트를 고쳐도, AI 엔지니어가 서버를 다시 배포해야 반영됐다. 프롬프트 개선이 서버 배포에 묶여 있었다.

그렇다고 프롬프트만 바로 교체할 수도 없었다. LLM 출력은 비결정적이라, 작은 수정으로도 채점 품질이 달라질 수 있다. 그런데 병합 전에 자동으로 평가하는 절차가 없어서, 변경 전후의 품질을 사람이 직접 확인해야 했다. 게다가 프롬프트를 바꾸면 품질뿐 아니라 지연시간과 비용도 함께 달라졌다. 지표 하나만 보고 새 버전을 채택할 수는 없었다.

그래서 [사례 2]({{ '/portfolio/quality-loop/' | absolute_url }})에서 만든 품질 측정 수단을, 변경을 채택하고 운영에 반영하는 절차에 연결해야 했다.

## 판단

**프롬프트 교체는 서버 배포에서 분리하되, 변경의 채택은 자동 평가와 사람 검토를 거치게 했다.**

분리와 검증은 한 번에 하지 않고 순서대로 붙였다. 먼저 코드 안 문자열을 YAML 파일로 옮겼다. 프롬프트를 읽고 고치기는 쉬워졌지만, 여전히 서버와 함께 배포해야 했다. 그래서 프롬프트 저장소와 Langfuse로 분리했다. 이제 버전을 관리하고 서버 재배포 없이 교체할 수 있었다. 그러자 새 문제가 생겼다. 서버 배포라는 관문이 사라졌으니, 변경 후의 품질을 확인할 절차가 따로 필요했다. 마지막으로 PR 평가 게이트와 staging 테스트를 붙였다.

게이트의 역할은 좁게 잡았다. 기준 미달처럼 명백한 문제는 자동 검사가 막는다. CI가 실패하면 병합할 수 없다. 하지만 품질·지연시간·비용이 서로 엇갈리면 자동으로 정할 수 없다. 그때는 사람이 평가 리포트와 변경 목적을 보고 최종 채택한다. 미세한 차이만으로 변경을 막지도 않았다. 기준 버전과 큰 차이가 없으면, 왜 프롬프트를 바꿨는지 확인하고 대체로 병합한다. 지표별 임계치는 현재 조정 중이다.

운영에 반영하기 전에는 학생에게 보이지 않게 확인한다. staging 환경에서 변경된 프롬프트와 workflow를 실제 운영 데이터로 테스트한다.

검토했지만 고르지 않은 대안은 다음과 같다.

| 대안 | 장점 | 고르지 않은 이유 |
|---|---|---|
| YAML 파일 분리에서 멈춤 | 프롬프트를 읽고 고치기 쉬워진다. | 여전히 서버와 함께 배포해야 한다. |
| 자동 평가만으로 채택 결정 | 사람의 검토 시간이 들지 않는다. | 품질·지연시간·비용이 엇갈리면 변경 목적을 아는 사람이 판단해야 한다. |
| 운영 A/B 테스트 | 실제 트래픽으로 비교할 수 있다. | 성능이 떨어질 수 있는 버전을 학생에게 보여 줘야 한다. |

## 구현

{% include diagrams/prompt-cicd-gate.html %}

프롬프트 변경은 PR에서 시작한다. 평가 데이터셋으로 기준 버전과 비교하고, 실패하면 PR 코멘트에 실패 원인·문제 샘플·개선 제안이 남는다. 작성자는 이를 보고 고친다. 자동 평가를 통과하면 사람이 리뷰한다.

리뷰를 통과하면 staging 브랜치에 병합하고, 실제 운영 데이터로 E2E 테스트를 한다. 결과는 학생에게 노출하지 않는다. 그다음 개발자가 최종 채택해 운영 브랜치에 병합한다. 프롬프트는 Langfuse에 새 버전으로 등록하고 production label을 옮긴다. Langfuse의 프롬프트 변경 webhook이 이를 AI 서버에 반영한다. 반영 후의 품질은 사례 2의 운영 표본 평가·대시보드·임계값 알림으로 확인한다.

재배포 없이 바꿀 수 있는 범위도 정했다. 프롬프트 변경은 서버 재배포 없이 반영하지만, workflow 코드가 바뀌면 서버 배포가 필요하다. AI 서버는 이전·새 프롬프트 I/O 계약을 함께 지원한다. 그래서 호환 범위 안이면 계약이 다른 버전 사이에서도 교체·롤백할 수 있다.

문제가 생겼을 때의 경로는 심각도에 따라 나눴다.

| 상황 | 대응 경로 |
|---|---|
| 일반 변경, 치명적이지 않은 문제 | 평가 게이트와 사람 검토를 거쳐 새 버전을 반영한다. |
| 치명적 문제 | Langfuse production label을 직전 버전으로 되돌리고, webhook으로 반영한다. |
| 롤백으로 해결할 수 없는 핫픽스 | Langfuse에 수동으로 등록한다. 평가 게이트를 우회하는 예외 경로다. |

### AI Agent 파일럿

평가 게이트가 없던 초기에는 비개발자가 Langfuse Playground·Experiments에서 결과를 눈으로 확인했다. 문제를 찾으면 프롬프트 엔지니어나 개발자에게 전달했다. 실제 수정은 주로 이 두 직군이 맡았다. 그래서 비개발자의 작업 절차만 개선해서는 효과가 작았다.

상황은 콘텐츠팀이 AI 결과를 확인하는 작업이 늘면서 달라졌다. 과제 유형이 늘수록 확인할 결과도, 고칠 프롬프트도 많아졌다. 그래서 채점 기준, Langfuse Trace, 프롬프트 수정, 평가 게이트를 연결한 사내 Agent 서비스를 개발했다. 실제 채점 로그 조회, 오채점 패턴에 따른 프롬프트 수정, 평가 게이트 실행을 각각 Skill로 구성했다. 그러자 2~3일 걸리던 프롬프트 개선 작업이 2~3시간으로 줄었다(Jira 스토리 포인트 기준).

지금은 사람이 작업을 판단하고, Agent가 해당 단계를 실행한다. 프롬프트 엔지니어와 개발자가 쓰는 파일럿이며, 최종 변경 채택과 운영 반영은 개발자가 맡는다. 다음 목표는 모델이 Skill을 스스로 연결해 개선 워크플로우를 수행하는 것이다.

## 한계와 다음 단계

- **병합 임계치는 아직 조정 중이다.** 품질·지연시간·비용과 변경 목적을 함께 봐야 해서, 숫자 하나로 정하기 어렵다. 수용 기준은 팀 논의로 조정하고 있다.
- **staging에서 확인한 데이터가 운영 전체를 대표하지는 않는다.** 그런데 운영에 반영하면 전체에 한 번에 적용된다. 놓친 문제는 운영 표본 평가가 잡을 때까지 학생에게 영향을 줄 수 있다. 다음 단계는 카나리 배포처럼 적용 범위를 나누는 것이다.
- **재배포 없는 교체에는 호환 범위가 있다.** 서버가 지원하지 않는 I/O 계약을 쓰거나 workflow 코드가 바뀌면, 서버를 고쳐 다시 배포해야 한다.
- **Agent 서비스는 파일럿이다.** 지금은 작업 판단을 사람이 맡는다. 모델이 Skill을 연결해 워크플로우를 자동으로 수행하도록 개선 중이다. 작업 시간 단축은 프롬프트 엔지니어와 개발자가 쓴 파일럿 기준이다. 콘텐츠팀으로 사용을 넓혔을 때의 효과는 추가 확인이 필요하다.
